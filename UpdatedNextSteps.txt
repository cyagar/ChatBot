This document supersedes the 24 August 2026 rewrite plan and its 25 August

plan, not a claim that the present demo is production-ready.


1. EXECUTIVE DECISION

Keep the native Kotlin/Jetpack Compose Android application and continue toward
the production architecture already selected in the original plan:

- Android is the technician client for phones and tablets; no WebView.
- A versioned Node.js/TypeScript API is the only public application service.
- Python remains internal for RAG, provider validation, extraction, OCR, and
  ingestion.
- PostgreSQL/pgvector becomes the source of truth.
- A durable queue plus transactional outbox owns answer and ingestion jobs.
- Private object storage serves manuals and rendered evidence.
- Redis or an equivalent managed service is used only for distributed limits,
  locks, short-lived event delivery, and cache.
- The administrator experience remains web-based. The current FastAPI/Jinja
  admin may remain temporarily behind an agreed retirement date; Next.js is
  still the target control plane.

Do not discard the working Android vertical slice. Stabilize it first, freeze its
behavior in tests, and then replace the temporary API/auth/storage boundaries one
vertical path at a time.


2. CURRENT IMPLEMENTATION AT THE REVIEWED COMMIT

2.1 Native Android work completed

- A native Kotlin/Compose application exists under android/; it is not a WebView.
- The app implements sign-in, machine search, recent/favorite indicators,
  conversation creation, chat, clarification, failed-answer retry, feedback,
  saving, conversation history/resume, citations, evidence page images, and
  pull-to-refresh.
- Expanded windows use a two-pane machine/history plus chat layout. Narrower
  windows use a single-pane flow. The decision is based on window width, not a
  device-model check.
- Warnings, revision conflicts, and no-answer states have distinct, non-color-only
  presentation.
- The session cookie is encrypted at rest with an Android Keystore AES-GCM key.
- Question submission sends a stable per-turn Idempotency-Key, and a manual retry
  reuses that key.
- The repository documents live checks on a Galaxy Tab A9+, including rotation,
  two-pane selection, session persistence, pull-to-refresh, history/resume, and
  accessibility-node inspection.
- There are 29 Android JVM test methods across cookie serialization and the login,
  machine, history, and chat ViewModels.

2.2 Backend work completed

- The existing FastAPI backend remains the active API, PWA, and administrator
  service.
- SQLite migrations 0010 and 0011 add per-conversation question idempotency and a
  unique saved-answer constraint.
- Duplicate question keys cannot insert two user turns. A completed duplicate can
  replay its original assistant response.
- Message hydration now returns the current user's latest feedback rating and
  saved status, allowing Android state to rehydrate after navigation/restart.
- Conversation history/resume is exposed to Android.
- Grounding validation now permits the selected machine's own name while still
  rejecting unrelated unsupported identifier/material tokens.
- Existing retrieval, approval, revision, ingestion, invitation, concurrency,
  citation, prompt-injection, and provider-contract protections remain present.

2.3 Work still explicitly in demo form

- Android talks directly to unversioned /api FastAPI routes.
- Authentication is a long-lived browser-style cookie, not OIDC/OAuth with PKCE.
- Chat is one synchronous POST; there is no answer-attempt resource, outbox,
  durable queue, status endpoint, or resumable event stream.
- Data remains in SQLite and local object storage; scheduling and locks are
  process-local.
- There is no Node.js mobile API, PostgreSQL/pgvector deployment, managed queue,
  Redis coordination layer, private production object storage, or Next.js admin.
- Android has no Room/DataStore draft persistence, Hilt, generated API client,
  build flavors, release endpoint, release signing pipeline, crash telemetry,
  minimum-version enforcement, or instrumented UI tests.
- minSdk 26, version 0.1.0-demo, and the release endpoint are placeholders.
- The app has been exercised on a Galaxy Tab A9+, but not on a real Android phone.

4. PHASE 0A -- FIX CURRENT DEMO BLOCKERS FIRST

These are not long-term architecture items. They are correctness, privacy, and
reproducibility gaps in the current Android demo and should be fixed before a
wider technician demonstration.

P0A-1. Enforce an account boundary and add logout

Current evidence:

- ApiService defines logout(), but the Android UI never calls it and exposes no
  logout control.
- AppNav redirects to login after a 401 but does not clear the activity-scoped
  selected conversation ID/label.
- A later login can therefore reopen the prior account's conversation ID/label
  and may retain user-scoped screen state until the unauthorized reload fails.

Required change:

- Add a visible logout action reachable from every signed-in layout.
- Call server logout when reachable, then always clear the local credential.
- On logout, 401, account disablement, and successful login as a different user,
  clear selected conversation, drafts, cached machines/history, evidence, and all
  user-scoped ViewModels/repositories.
- Validate the stored session through /me on launch instead of treating the mere
  presence of a cookie as proof of a valid signed-in user.
- Reject or redirect administrator accounts from the technician app unless the
  owner explicitly approves admins using it.
- Add tests for user A -> logout/expiry -> user B, including two-pane mode and a
  previously open citation.

Exit gate: No state, label, message, evidence, saved status, or selection from one
account is visible after another account signs in.

P0A-2. Correct the unresolved 409 answer state

Current evidence:

- The backend returns 409 when a duplicate idempotency key has a persisted user
  turn but no assistant reply yet.
- Android then refreshes messages.
- ChatViewModel.loadMessages() unconditionally clears pendingEcho and
  pendingEchoUncertain on any successful GET, even when the response contains only
  the user turn. The retry/processing affordance can disappear while no answer
  exists, especially after a server crash.
- The existing 409 Android test only covers the favorable case where refresh
  immediately returns an assistant answer.

Required interim change:

- Add a regression test where POST returns 409 and GET returns only the user turn.
- Preserve an explicit "accepted/unknown or still processing" state and a manual
  refresh action until an assistant result is present.
- Ensure pull-to-refresh or an initial load cannot clear an in-flight local echo.
- Do not create a new key or a second user turn.

Permanent fix: Phase 2 must replace this ambiguous row-order inference with a
durable answer-attempt resource and server-authoritative status.

Exit gate: A dropped connection or server restart can never leave a question that
looks complete, silently disappears, or loses its recoverable status.

P0A-3. Remove Android request-order and partial-success races

Current evidence:

- MachinesViewModel starts an uncancelled search coroutine on every keystroke.
  An older, slower response can overwrite results for the current query.
- After createConversation succeeds, selectMachine awaits a separate touchMachine
  call before navigating. If that secondary call throws, the conversation exists
  server-side but Android reports total failure and does not open it; a retry can
  create an extra empty conversation.
- Chat refresh and send can run concurrently, while loadMessages clears pending
  state without checking whether a send is active.

Required change:

- Debounce machine search, cancel the prior search job, and apply results only if
  their query still equals the current query.
- Make recent-machine recording part of successful conversation creation on the
  server, or navigate immediately after creation and make touch best-effort and
  independently observable.
- Serialize or merge chat refresh/send state so refresh cannot erase an in-flight
  or uncertain question.
- Add deterministic delayed-response tests for all three races.

Exit gate: Stale responses cannot replace current results, and a secondary
analytics/convenience failure cannot turn a committed conversation into a visible
failure.

P0A-4. Fix navigation and evidence failure handling

Current evidence:

- Routes.chat() interpolates machineLabel directly into a navigation query string.
  Real model labels contain reserved characters such as "/"; future labels may
  contain "&", "?", or "%".
- Citation evidence requests silently close/fall through on non-2xx responses or
  exceptions; no useful error or retry is shown.

Required change:

- Prefer passing only conversationId and loading its machine label from the
  server. If a label remains a route argument, URI-encode and decode it.
- Model evidence as loading/success/error, check isSuccessful before body(), and
  offer retry without losing the citation context.
- Add route tests with AJ/AJX-style labels and evidence tests for 401, 403, 404,
  500, timeout, and image-load failure.

Exit gate: All valid machine labels navigate correctly, and evidence failures are
honest, recoverable, and accessible.

P0A-5. Make compact-phone and large-text layouts genuinely safe

Current evidence:

- Clarifying choices, citation chips, and Helpful/Incorrect/Save actions use plain
  Rows that do not wrap or scroll.
- These can overflow at 360-430dp phone widths, with long model/manual names, or
  under large font scaling.
- No real phone or instrumented screenshot/accessibility suite has verified the
  expanded device requirement.

Required change:

- Use FlowRow, responsive stacking, or horizontal scrolling as appropriate.
- Keep warning text and primary repair actions visible before secondary actions.
- Test 360dp, 411dp, Medium tablet, Expanded tablet, portrait, landscape,
  split-screen, 200 percent font scale, display scaling, keyboard open, and long
  localized-like strings.
- Perform a human TalkBack session to verify error live-region announcements and
  logical focus order; accessibility-node inspection alone is insufficient.
- Test at least one real phone plus the lowest-spec Galaxy Tab A9+ fleet unit.

Exit gate: No clipping, unreachable action, horizontal truncation, or focus-order
failure exists in the supported matrix.

P0A-6. Repair build, credential, and documentation hygiene

Current evidence:

- The public repository includes a plaintext demo credential in android/README.
- The debug API host is a hardcoded LAN address and the release endpoint is
  https://CHANGE-ME.invalid/.
- gradlew lacks its Unix executable bit.
- The Gradle daemon JDK 25 requirement and Android SDK 37 requirement are not
  documented as developer/CI prerequisites.
- android/README contains stale/contradictory statements: an early section says no
  physical-device run occurred, while later sections document multiple live Tab
  A9+ verifications; its Android test counts are also outdated.

Required change:

- Remove the committed demo password, rotate/delete that account anywhere it was
  seeded, and replace manual SQL seeding with a repeatable dev-only script or
  environment-controlled fixture.
- Commit gradlew as executable and document the exact supported Android Studio,
  daemon JDK, Android SDK, and build commands; remove accidental host-specific
  toolchain criteria if they are not intentional.
- Add development, staging, and production endpoint configuration without source
  edits or hardcoded personal LAN addresses. Release builds must fail when no real
  HTTPS endpoint is configured.
- Update Android documentation to one truthful current-state section.
- Tag the reviewed baseline before the next implementation series.
- Isolate mocked provider tests from ambient proxy settings or explicitly install
  and test the supported proxy transport.

Exit gate: A fresh developer/CI environment can build and test from documented
inputs; no known credential or placeholder endpoint can ship.

- Add stable cursor pagination for machines, history, messages, and saved answers.
- Return UTC ISO-8601 timestamps with offsets.
- Bootstrap the Node.js/TypeScript public API and keep Python services private.
- Implement Authorization Code with PKCE through the system browser/custom tab,

Exit gate: A clean staging Android install signs in with the approved identity

7. PHASE 2 -- POSTGRESQL, DURABLE ANSWER ATTEMPTS, AND RECONNECT

Deliverables:

- Migrate the required vertical-slice tables to PostgreSQL: users/identity map,
  machines, approvals, documents/chunks, conversations/messages, answer_attempts,
  citations, idempotency, feedback/saves, outbox, and audit records.
- Create answer_attempt with explicit queued/running/completed/failed/cancelled
  states, retry lineage, timestamps, and terminal error codes.
- Require a valid Idempotency-Key on question creation; bind it to user,
  operation, and request fingerprint. Reject missing, blank, malformed, or reused
  keys with a different payload.
- Commit user message, attempt, and outbox row in one PostgreSQL transaction.
- Process jobs through a durable queue. Persist every authoritative status/event.
- Return 202 with messageId, attemptId, status URL, and event URL.
- Add resumable Server-Sent Events with event IDs, heartbeat, bounded stream life,
  and a final event; status polling remains authoritative.
- Make retry create a new auditable attempt for the same user turn without a
  duplicate message. Preserve prior attempt metadata.
- On Android, persist draft, conversation ID, attempt ID, and last event ID using
  SavedStateHandle/Room/DataStore as appropriate. Reattach after rotation, process
  death, app restart, or network change without resubmitting the question.
- Support honest cancellation semantics: stopping display is distinct from safely
  cancelling server work.

Tests:

- Duplicate taps, concurrent duplicate keys, same key/different payload, commit
  before queue outage, worker crash, API restart, queue delay, provider timeout,
  stream drop, duplicate/out-of-order events, process death, and reconnect after
  completion.
- Assert exactly one user turn and one original attempt for one accepted key.
- Assert an incomplete stream is never rendered as a verified final answer.

Exit gate: Every server-accepted question has a recoverable authoritative attempt;
there is no 409 dead end and no client-side inference from adjacent message rows.

12. RELEASE-BLOCKING BACKEND AND CORPUS ITEMS THAT MUST NOT DISAPPEAR

Track these explicitly even when the Android team is focused elsewhere:

- The 71-document grandfather approval and unreconstructible historical Drive
  source pairing require a business-approved remediation and published mapping.
- Backup/restore has not been rehearsed.
- Multi-user concurrent load has not been measured; SQLite is not a multi-replica
  production database.
- In-process ingestion scheduling/jobs do not survive crashes or coordinate
  replicas.
- Automatic pipeline reprocessing and revision supersession are incomplete.
- Source deletion/quarantine reconciliation is incomplete.
- OpenAI live-provider behavior, generative revision-conflict behavior, OCR quality
  at scale, and real legacy .doc quality remain unverified.
- Short unsupported bare-code queries can return low-information but honestly cited
  passages; add a focused evaluation set before changing thresholds.
- If the PWA is retained as fallback, its browser UI, service worker, offline cache,
  account disablement, shared-device account switch, and retry controls require
  real-browser verification.

15. BUILDER RULES

1. Do not call the present app production-ready because it builds or works on one
   tablet.
2. Do not delete or weaken a safety/concurrency test to make a migration pass.
3. Treat server state as authoritative for identity, machine scope, approval,
   revision, attempts, citations, and final-answer status.
4. Never place AI keys, database/Drive/object-storage credentials, manuals,
   embeddings, or an on-device model in the APK.
5. Never infer a machine switch silently.
6. Never render a partial stream as a verified answer.
7. Every feature change includes its failure, account-switch, accessibility, and
   process-death behavior where applicable.
8. Every migration has reconciliation and rollback evidence.
9. Every release claim is supported by CI output, a staging trace, a migration or
   restore report, or a physical-device checklist/recording.
10. Stop for owner input at the decision gate; do not invent identity, retention,
    BYOD, cache, or corpus-approval policy.

re-estimate after Phase 1 and the durable vertical slice. This is not a delivery
