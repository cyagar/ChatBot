ADDENDUM -- 25 August 2026: DEVICE SCOPE EXPANDED TO PHONES

This plan was written for the Galaxy Tab A9+ tablet fleet specifically, and
the body text below (including its title) still reflects that original
scope -- it has not been rewritten. That scope has since changed: technicians
will also use this app on their personal or company Android phones, not only
the tablet fleet. Everywhere below that reads "tablet," "Tab A9+," or assumes
one specific 11-inch device, read it as "the primary reference device for the
original one-day slice," not as the current device requirement.

The current requirement is that the app work correctly and look good on any
Android device -- phone or tablet, any screen size -- not just the Tab A9+.
Practically, this means:

- Layout must be driven by Material 3 window-size classes (Compact/Medium/
  Expanded), never by device model or a hardcoded "is this a tablet" check.
  See android/README.md's "Material 3 Adaptive list-detail layout" entry:
  the two-pane layout already gates on WindowWidthSizeClass.Expanded, which
  a phone will essentially never reach in either orientation, so it already
  falls back to the original single-pane flow there without any extra work.
- Touch targets, text scaling, and spacing need to hold up at phone-portrait
  widths (~360-430dp), not just at tablet scale. This has been reasoned
  through and spot-checked with a simulated phone resolution/density on the
  Tab A9+ (see android/README.md) but not yet verified on real phone
  hardware.
- Section 6 ("GALAXY TAB A9+ DESIGN TARGET") and its device-inventory,
  fleet-QA, and MDM/Knox-specific asks (sections 18-19) still describe real,
  still-needed work for the tablet fleet specifically -- they are not
  superseded, just no longer the *only* device class this app has to serve.

See android/README.md for what has actually been verified against this
expanded scope, since that file is kept current; this plan document is not.


1. EXECUTIVE DECISION

Rewrite the technician-facing experience as a native Android tablet application.
Do not package the current website in a WebView, do not rely on the existing PWA,
and do not put an AI model, manuals, embeddings, database credentials, Google
Drive credentials, or AI-provider keys in the APK.

The Galaxy Tab A9+ should be a fast, simple, secure client. Retrieval, answer
generation, manual ingestion, approvals, and the source-of-truth conversation
record should remain on an internet-hosted production platform.

Target product split:

- Native Android technician app: Kotlin, Jetpack Compose, Material 3 Adaptive.
- Public application API: Node.js and TypeScript.
- Web administrator/control plane: Next.js and TypeScript.
- RAG, extraction, OCR, embedding, and ingestion: internal Python services/workers.
- Data: PostgreSQL plus pgvector.
- Durable jobs and distributed coordination: a managed queue and Redis or an
  equivalent managed coordination service.
- Manual files: private object storage, with Google Drive retained as the manual
  source of truth unless the business changes that policy.

This division satisfies the earlier production-architecture requirement without
forcing machine-learning code into Node.js. Node.js owns the public API,
authentication integration, authorization, request lifecycle, and admin control
plane. Python remains an internal implementation detail for the work it is best
suited to. Only the Node.js API is exposed to the Android app.


2. WHAT THE CURRENT PROJECT ALREADY HAS

The baseline is a FastAPI, Jinja2, vanilla-JavaScript PWA backed by SQLite and
local object storage. It has no Android project or native tablet client.

The following behavior is valuable and must be preserved through the rewrite:

- Invitation-controlled accounts and account disabling.
- Machine search, recent machines, and favorites.
- Explicit machine selection and explicit machine changes.
- Machine-scoped retrieval enforced before answer generation.
- Conversation history and conversation resumption.
- Clarifying machine choices without duplicating the pending technician question.
- Structured answers, source citations, manual evidence, page images, warnings,
  revision-conflict notices, and honest no-answer behavior.
- Retry without inserting a duplicate user turn.
- Saved answers and technician feedback.
- Google Drive ingestion, checksums, idempotency, review approval, revision status,
  duplicate detection, pipeline-version drift detection, and ingestion reports.
- Admin review, query testing, feedback review, unanswered-question review, and
  audit history.
- Provider contract validation and grounding safeguards.

The Android rewrite must not regress these invariants while changing the user
interface and infrastructure.


3. CURRENT LIMITATIONS THAT THE REWRITE MUST REMOVE

1. The technician UI is a browser PWA, not an Android application.
2. Cookie-based browser sessions are not an appropriate long-term native mobile
   authentication contract.
3. The current chat request performs retrieval and generation synchronously; it
   lacks a durable answer-attempt resource and resumable streaming contract.
4. SQLite, local object storage, process-local rate limiting, and an in-process
   scheduler are single-instance constraints and are not the requested production
   architecture.
5. The public API is not versioned specifically for independently released mobile
   clients.
6. Several list endpoints use simple limits instead of stable cursor pagination.
7. Manual files and rendered pages are served from the application instance's
   local disk.
8. Frontend caching depends on a service worker and manual cache-version changes.
9. There is no mobile release pipeline, managed-device rollout, crash telemetry,
   minimum-supported-version control, or physical-device test suite.


4. SCOPE AND NON-GOALS

In scope:

- A production native Android application optimized for Galaxy Tab A9+ tablets.
- Internet-based chat with a resilient reconnect/resume experience.
- A stable, documented, versioned mobile API.
- Production authentication, authorization, storage, queueing, observability,
  security, CI/CD, managed distribution, pilot, and cutover.
- Migration of existing approved manuals, users, machine data, conversations,
  feedback, saved answers, citations, and audit-relevant records.
- Retention of a web administrator interface.

Not in scope for this rewrite:

- Running an LLM or vector search on the tablet.
- Answering questions without internet.
- Downloading the complete manual library to every tablet.
- Rebuilding ingestion, manual review, or user administration as Android screens.
- A WebView wrapper around the present site.
- A public consumer app or public self-registration.
- Silent machine changes inferred from later chat messages.

When connectivity is lost, the app should preserve an unsent draft, explain that
an internet connection is required, and allow a submitted server-side attempt to
be resumed after reconnection. It must not invent an offline answer. Do not queue
a new question invisibly for later submission unless product owners explicitly
approve that behavior; delayed submission could be unsafe or confusing at a
machine site.


5. TARGET PRODUCTION ARCHITECTURE

5.1 Technician request path

1. The Android app authenticates through the organization's identity provider.
2. The app calls the versioned Node.js mobile API over HTTPS.
3. The Node.js API authenticates and authorizes the technician, validates the
   selected machine, applies rate limits, creates the user message and an answer
   attempt in PostgreSQL, and records an idempotency key.
4. A durable job is created transactionally, using an outbox or equivalent
   mechanism so a database commit cannot be separated from job delivery.
5. An internal worker invokes the Python RAG service against the approved,
   current, selected-machine corpus in PostgreSQL/pgvector.
6. The RAG service retrieves evidence, calls the configured AI provider, validates
   structured claims/citations/warnings, and returns a grounded result.
7. Attempt status and events are persisted. The Node.js API streams progress and
   answer events to the Android app using Server-Sent Events over HTTPS.
8. If the stream or app process closes, the app reconnects using the attempt ID or
   fetches the completed result. Reconnection never resubmits the user question.

5.2 Services

- android-app: Native technician UI; no privileged backend credentials.
- mobile-api: Node.js/TypeScript service. Recommended framework: NestJS with the
  Fastify adapter, or another approved TypeScript framework with equivalent
  validation, OpenAPI, security, testing, and observability support.
- admin-web: Next.js/TypeScript administrator UI calling the same control-plane
  API. The current admin UI may remain temporarily during migration.
- rag-service: Internal Python service containing retrieval, provider adapters,
  structured-output validation, citation validation, and safety logic.
- ingestion-worker: Python worker for Drive sync, extraction, OCR, metadata,
  chunking, deduplication, embedding, and index updates.
- job-worker: Durable orchestration for answer and ingestion jobs. Use a
  cross-language managed queue, RabbitMQ, or an equivalent platform chosen for
  the hosting environment. Do not use an in-process background loop as the
  production scheduler.
- postgres: PostgreSQL source of truth with pgvector for embeddings.
- object-storage: Private, encrypted storage for original manuals and rendered
  evidence pages.
- coordination/cache: Redis or equivalent for distributed rate limiting,
  short-lived event fan-out, locks, and cache only; PostgreSQL remains the source
  of truth.

5.3 Security boundaries

- Only the Node.js API and the identity provider are reachable from the tablet.
- RAG, worker, database, queue, Redis, Drive credentials, and object storage are
  private network resources.
- Every manual/evidence access is authorized server-side. Use an authenticated
  streaming endpoint or a very short-lived signed URL bound to an authorized
  request.
- Store no AI-provider key, database secret, Drive service-account credential, or
  object-storage master credential in the APK.
- Use TLS only and reject cleartext traffic through Android Network Security
  Configuration.
- Redact tokens, questions, answers, manual excerpts, and proprietary identifiers
  from routine mobile logs, crash reports, and analytics.
- Certificate pinning is optional, not a default. Adopt it only with a tested
  certificate-rotation and emergency-recovery process.


6. GALAXY TAB A9+ DESIGN TARGET

Official Samsung information describes the Galaxy Tab A9+ as an 11-inch tablet
with a 1920 x 1200-class display, refresh rate up to 90 Hz, 64 GB or 128 GB
storage options, microSD support, multi-window support, and optional 5G variants.
The app should take advantage of its tablet display without depending on one exact
storage or connectivity variant.

Before setting Android SDK support rules, inventory the actual company fleet:

- Exact Samsung model/SKU and whether each device is Wi-Fi-only or cellular.
- Memory and storage variant; test against the lowest-memory unit in the fleet.
- Installed Android/One UI version and security-patch level.
- Managed-device platform, work profile, VPN, certificates, and identity provider.
- Rugged case, gloves, external keyboard, barcode scanner, or DeX use.
- Site network restrictions, captive portals, proxy/VPN, and expected weak-signal
  conditions.

Do not guess minSdk from the product name. Set minSdk to the oldest managed fleet
OS after inventory. Set compileSdk and targetSdk to the current stable/required
levels at release time, and keep them current through normal maintenance.

Required layouts and behavior:

- Portrait, landscape, split-screen, multi-window, and Samsung DeX.
- Material 3 adaptive window-size classes, not device-model checks.
- Wide mode: machine/history navigation beside the active conversation where it
  improves speed; compact mode: a clear single-pane flow.
- Minimum 48 dp touch targets, readable typography, strong contrast, and generous
  spacing for technicians working on site.
- Correct back navigation, keyboard behavior, rotation/state restoration, process
  death restoration, and edge-to-edge system bars.
- TalkBack labels, logical focus order, font scaling, color-independent status,
  and accessible citation/manual controls.
- No background embedding, OCR, model execution, or corpus download that wastes
  battery, storage, or memory.


7. ANDROID TECHNOLOGY DECISIONS

Use:

- User who owns the project is using Android Studio
- Kotlin and Gradle Kotlin DSL.
- Jetpack Compose and Material 3 Adaptive.
- Single-activity navigation with Navigation Compose.
- Layered architecture: UI, domain/use cases where useful, and data repositories.
- Unidirectional data flow, immutable screen state, ViewModels, coroutines, and
  StateFlow.
- Hilt for dependency injection.
- Retrofit plus OkHttp, or Ktor Client, with kotlinx.serialization. Select one
  HTTP stack and use it consistently.
- An OpenAPI-generated model/client layer where it produces maintainable code;
  wrap generated code behind repositories so API regeneration does not leak into
  the UI.
- Room only for minimal non-sensitive data such as drafts, machine-list cache,
  conversation metadata, and pending feedback where policy permits.
- DataStore for ordinary preferences. Use an Android Keystore-backed token vault
  for authentication secrets; never store refresh tokens as plain preferences.
- WorkManager for non-urgent resilient work such as telemetry or explicitly
  approved feedback delivery. Do not run the live chat answer inside WorkManager.
- Coil for authorized page images and thumbnails, with a cache policy that avoids
  retaining protected evidence longer than approved.

Codebase modules should begin simple and become modular only along clear product
boundaries. A suitable initial structure is:

- app
- core:model
- core:network
- core:database
- core:designsystem
- core:testing
- feature:auth
- feature:machines
- feature:chat
- feature:history
- feature:saved
- feature:manual
- feature:settings

Do not create dozens of empty modules at the start. Establish conventions with
one complete vertical slice before copying the pattern.


8. MOBILE AUTHENTICATION PLAN

Preferred production choice:

- Enterprise OpenID Connect/OAuth using Authorization Code with PKCE.
- Launch authentication through the system browser/custom tab with an established
  AppAuth-compatible implementation; do not embed credentials in a WebView.
- Short-lived access tokens, rotating refresh tokens, server-side revocation,
  audience and issuer validation, device clock-skew handling, and logout that
  clears both server and local state.
- Map identity-provider groups/claims to technician and administrator roles on the
  server. The Android app is for technicians; administrators use the web portal.

If the organization has no identity provider, retain invitation-controlled email
and password accounts temporarily, but add a proper mobile token endpoint rather
than relying on the browser session cookie. Keep invitations single-use,
email-bound, expiring, and race-safe. Plan migration to enterprise SSO after the
pilot.

Required authentication tests include expired access tokens, refresh rotation,
reuse detection, disabled users, revoked devices, invalid audiences, device clock
skew, app process death, password/SSO cancellation, and logout on another device.


9. VERSIONED MOBILE API CONTRACT

Create a new contract under /api/v1/mobile (or an equivalent versioned host).
Do not make the Android app scrape HTML or depend directly on Jinja/PWA behavior.
Publish OpenAPI in CI and make incompatible schema changes require a new API
version or a backward-compatible migration window.

Recommended resources:

- GET  /config
  Minimum supported app version, feature flags, maintenance state, support link,
  and safe user-facing status messages.

- GET  /me
  Current user and allowed capabilities.

- GET  /machines?query=&cursor=&limit=
- GET  /machines/recent?cursor=&limit=
- PUT  /machines/{machineId}/favorite
- POST /machines/{machineId}/usage

- POST /conversations
- GET  /conversations?cursor=&limit=
- GET  /conversations/{conversationId}
- GET  /conversations/{conversationId}/messages?cursor=&limit=
- PUT  /conversations/{conversationId}/machine

- POST /conversations/{conversationId}/questions
  Requires an Idempotency-Key header. Persist the question and return 202 with
  messageId, attemptId, status, and stream URL. A duplicate key for the same user
  and payload returns the original result, not another user message.

- GET  /answer-attempts/{attemptId}
- GET  /answer-attempts/{attemptId}/events
  Resumable Server-Sent Events with event IDs, heartbeat, bounded lifetime, and a
  final event. The normal status endpoint remains authoritative.

- POST /messages/{assistantMessageId}/retry
  Creates a new auditable attempt for the same user turn without inserting a
  duplicate user message. The UI presents the current attempt while the database
  preserves attempt history for support and audit.

- POST /messages/{assistantMessageId}/feedback
- PUT  /messages/{assistantMessageId}/saved
- GET  /saved-answers?cursor=&limit=

- GET  /citations/{citationId}/evidence
- GET  /manuals/{documentId}/pages/{pageNumber}/image
- GET  /manuals/{documentId}/file
  Support authenticated byte ranges or short-lived signed delivery. Authorize
  approved/current status on every request; never trust an old citation alone.

Contract rules:

- Use stable cursor pagination for growing collections.
- Return UTC ISO-8601 timestamps with timezone information.
- Use one naming convention consistently.
- Return a machine-readable error code, safe display message, request/correlation
  ID, retryability flag, and field errors where relevant.
- Support cancellation and server timeouts.
- Retry only idempotent operations automatically. Never blindly retry a question
  POST without its idempotency key.
- Apply authorization, machine eligibility, approval, and current-revision rules
  on the server; the app's screen state is not a security boundary.


10. TECHNICIAN APP EXPERIENCE

10.1 Entry and machine selection

- Managed app launch and sign-in.
- Home screen with a prominent “Ask about a machine” action.
- Search by manufacturer, model, family, or approved alias.
- Recent and favorite machines.
- Always display the active manufacturer and model near the composer.
- Make “Change machine” explicit and confirm it when an answer context could be
  affected.
- If a question names multiple or ambiguous models, show the server-provided
  choices. Selecting one resumes the same pending question.

10.2 Chat

- Large composer, send/cancel action, optional suggested question examples, and
  visible character limit.
- Immediate local echo only after the server accepts the idempotent question, or
  a clearly marked sending state until accepted.
- Visible stages such as “Searching approved manuals” and “Preparing grounded
  answer”; do not expose internal chain-of-thought.
- Stream answer content safely, then render the server's final structured answer.
- Emphasize warnings before procedural steps.
- Clear no-answer, provider-unavailable, retrieval-unavailable, permission,
  maintenance, timeout, and weak-connection states.
- Retry the same attempt without duplicating the technician's question.
- Cancel the display stream independently of server job cancellation. If a job
  can be safely cancelled, expose that as a separate API operation.
- On process death or reconnect, reopen the conversation and fetch/reattach to the
  outstanding attempt.

10.3 Citations and manuals

- Every factual claim or step that requires support remains tied to evidence.
- Citation cards show manual title, revision, section, and page.
- An evidence bottom sheet shows the exact excerpt and page image.
- A full manual viewer opens at the cited page, supports zoom and page navigation,
  and clearly identifies the document/revision.
- Avoid downloading and retaining whole protected manuals by default. If product
  owners later approve downloads, add explicit expiration, encryption, removal,
  and MDM policy before enabling them.

10.4 History, saved answers, and feedback

- Resume recent conversations with stable titles.
- Preserve the selected machine and complete message/citation state.
- Search or filter history only after privacy and server-performance requirements
  are defined.
- Save/unsave useful answers.
- One-tap helpful/not-helpful feedback, followed by an optional reason. Never make
  feedback interrupt the repair task.

10.5 Optional later features

- Voice input, after testing speech recognition in noisy machine rooms and making
  microphone permission optional. Internet-based speech recognition is acceptable
  for this online product, but voice is not required for the first release.
- QR/barcode machine identification only after a reliable asset-to-model mapping
  exists. A scan must still show and confirm the resolved machine.
- Site/equipment asset integration only through a separately secured API.


11. PRODUCTION DATA AND BACKEND MIGRATION

11.1 PostgreSQL schema

Move users, roles, machines, aliases, documents, document-machine approvals,
chunks, conversations, messages, answer attempts, citations/sources, feedback,
saved answers, invitations if still used, ingestion runs/events, audit events,
and pipeline versions to PostgreSQL.

Add or confirm:

- UUID or other externally safe identifiers at public boundaries.
- Explicit answer_attempt records with state transitions and retry lineage.
- Idempotency-key records scoped to user and operation.
- Transactional outbox records for durable job creation.
- pgvector columns and suitable indexes after measuring the real corpus.
- Data retention and deletion fields.
- Optimistic concurrency/version fields where admin review races are possible.

11.2 Migration procedure

1. Take a verified SQLite backup and immutable object-storage snapshot.
2. Build repeatable export/import tooling; do not hand-edit production rows.
3. Re-ingest original manuals from Google Drive into private object storage and
   verify source reference, byte size, and checksum. Preserve review decisions and
   current-revision relationships through an explicit mapping report.
4. Migrate relational records in dependency order and retain a legacy-ID mapping.
5. Prefer regenerating embeddings with the approved model/pipeline version rather
   than copying opaque SQLite float blobs without provenance.
6. Preserve current password hashes temporarily if compatible, then rehash to the
   approved scheme at successful login. Invalidate browser sessions at cutover.
7. Compare row counts, checksums, foreign-key integrity, approved/current machine
   coverage, conversations, citations, saved answers, and feedback.
8. Run the full retrieval evaluation and safety regression suite on the migrated
   corpus before allowing technicians into production.
9. Produce a signed migration report and retain a tested rollback procedure.

Google Drive can remain the business source of truth, while private object storage
is the production serving copy. Scheduled ingestion should run through a managed
scheduler and durable worker, with locking so two syncs cannot process the same
corpus concurrently.

Exit gate: Under duplicate taps, dropped connections, rotation, process death, and
provider delay, there is exactly one user turn; the attempt completes or fails

PHASE 4 — GROUNDED ANSWERS, EVIDENCE, AND PARITY

Deliverables:

- Render structured claims, steps, warnings, conflict notices, and no-answer state.
- Implement citations, evidence sheet, authenticated page image, and manual viewer.

- Confirm exact parity for all technician-facing PWA behavior worth retaining.
- Make the Next.js admin portal capable of manual review, ingestion monitoring,
  query testing, user control, feedback review, and unanswered-question review;
  or formally retain the existing admin temporarily with an agreed retirement
  date and compatible production database/API.

Exit gate: Every answer shown to a technician can be reloaded with identical
sources and warnings, and evidence access respects approval and authorization.

PHASE 5 — PRODUCTION INFRASTRUCTURE AND MIGRATION

Deliverables:

- Complete PostgreSQL/object-storage migration tooling and reports.
- Replace local/process-only rate limiting, locks, scheduling, and storage.
- Configure backups, point-in-time recovery, restore tests, key rotation, alerts,
  autoscaling limits, cost controls, and incident runbooks.
- Complete security testing and privacy review.
- Run corpus ingestion and retrieval evaluation in the production-like staging
  environment.

Exit gate: A restore drill, migration rehearsal, rollback rehearsal, and production
readiness review all pass.

PHASE 6 — PHYSICAL-DEVICE PILOT AND CUTOVER

Deliverables:

- Publish the private app through managed Google Play and enroll pilot tablets
  through Android Enterprise or the organization's Samsung Knox/EMM platform.
- Pilot with a small representative technician group across real sites, machine
  families, orientations, cases, and network conditions.
- Collect task-completion, answer latency, no-answer, feedback, crash, ANR, and
  support data without capturing protected manual content in analytics.
- Fix pilot P0/P1 issues, train technicians, and publish a one-page support guide.
- Roll out in rings: engineering, internal operations, pilot technicians, broader
  fleet.
- Keep the PWA as an explicitly supported fallback during the pilot. Freeze it to
  security fixes, then make it read-only or retire technician access only after
  the Android acceptance gates pass.

Exit gate: Product owner, technician representative, security, and operations sign
off; rollback remains available through the stabilization window.


13. TEST STRATEGY

13.1 Android tests

- Kotlin/JUnit unit tests for reducers, ViewModels, use cases, parsing, auth state,
  idempotency, retry, and reconnect logic.
- Coroutine and Flow tests with controlled time.
- MockWebServer or equivalent tests for success, schema errors, 401/403/409/429,
  timeouts, malformed streams, duplicate events, reconnect event IDs, and partial
  responses.
- Compose UI tests for every core flow and accessibility semantics.
- Screenshot tests for compact/wide, portrait/landscape, font scaling, light/dark
  if supported, warnings, citations, and long model/manual names.
- Instrumented tests on actual company Galaxy Tab A9+ units, including the
  lowest-memory SKU, multi-window, DeX if used, rotation, low storage, process
  death, keyboard, VPN, and managed policy.
- Macrobenchmark and Baseline Profile tests for startup, scrolling, and chat
  rendering.

13.2 Backend and contract tests

- OpenAPI compatibility checks and generated-client compilation in CI.
- Unit, integration, migration, and end-to-end tests against PostgreSQL, queue,
  object storage, and the internal RAG service.
- Concurrent invitation, idempotency, retry, approval, ingestion, and admin-review
  race tests.
- Machine isolation, wrong-machine near-match, deactivated/unapproved/superseded
  manual, citation order, retry persistence, and clarification-resume regressions.
- Provider contract, prompt injection, unsupported claims, warning-verbatim,
  revision conflict, retrieval failure, and provider failure tests.
- Load tests for login, machine search, conversation lists, chat creation, event
  streams, and evidence delivery.

13.3 Network and resilience tests

- Slow Wi-Fi, high latency, packet loss, DNS failure, captive portal, proxy/VPN,
  network switch, connection drop during submit, stream drop after partial answer,
  reconnect after completion, server restart, queue delay, and provider outage.
- Confirm a duplicate tap or client retry never duplicates the question.
- Confirm a server-accepted attempt remains recoverable after the app is killed.
- Confirm the app never presents stale partial text as a verified final answer.

13.4 Security tests

- APK and source secret scans.
- No cleartext network traffic; correct hostname and certificate validation.
- Token theft/revocation and disabled-user tests.
- Authorization tests on every conversation, message, citation, manual, admin, and
  ingestion resource.
- Log/crash/analytics redaction checks.
- Dependency and container scanning, SBOM, signed artifacts, and patch process.
- Backup encryption and restore authorization.

13.5 Field usability tests

- Observe technicians completing representative repair questions without coaching.
- Measure time to select the machine, ask, identify a warning, open a citation,
  return to chat, save/feedback, and resume later.
- Test glare, noisy rooms, gloves/cases, landscape holding, weak network, and urgent
  interruption.
- Require technicians to identify the selected model and source revision before
  following a safety-critical instruction.


14. RELEASE AND OPERATIONS

Distribution:

- Prefer a private managed Google Play application for company-owned tablets.
- Use Android Enterprise fully managed or dedicated-device policy where these are
  company-owned work-only devices. Samsung Knox Manage or another EMM is suitable
  if it is already the organization's standard.
- Maintain development, staging, internal, pilot, and production tracks.
- Sign through controlled release infrastructure; protect and back up signing
  keys. Restrict production publishing permissions.
- Use staged rollouts and an API-provided minimum-supported-version policy. Provide
  a maintenance message and safe update path instead of allowing incompatible old
  clients to fail unpredictably.

Operations:

- Track crash-free sessions, ANRs, authentication failures, API errors, answer
  attempt state/latency, stream reconnects, retrieval no-answer rate, provider
  failure, ingestion freshness, queue depth, and evidence delivery errors.
- Never put question/answer/manual text in analytics by default. Use opaque IDs and
  approved aggregate metrics.
- Propagate a correlation ID from Android through Node.js, queue/worker, Python,
  provider call, and persisted attempt.
- Define on-call ownership, severity levels, a user-visible service status, manual
  ingestion failure response, account compromise response, and AI-provider
  fallback policy.
- Test remote account revocation and managed-device wipe/retirement.

Preliminary service objectives to validate during the pilot:

- Crash-free sessions at least 99.5 percent.
- ANR rate below 0.5 percent.
- First visible local progress within 300 ms after a successful server acceptance.
- First answer content p95 within 5 seconds and a typical short final answer p95
  within 15 seconds under the representative network, measured separately from
  provider outages and reviewed after baseline data exists.
- Zero secrets or protected manual text in routine logs/analytics.
- Zero cross-user or cross-machine evidence leakage in acceptance tests.


15. CUTOVER AND ROLLBACK

1. Keep the existing system unchanged except for necessary security and data-
   integrity fixes while the new platform is built.
2. Rehearse migration from a production-like copy at least twice.
3. Run the Android app against staging with the migrated corpus and test accounts.
4. Pilot Android while the PWA remains available as a controlled fallback.
5. Before final cutover, freeze writes briefly, export the final delta, migrate,
   validate counts/checksums/evaluations, change the API endpoint, and monitor.
6. If acceptance checks fail, direct devices back to the prior supported endpoint
   or PWA and restore the previous write owner. Do not attempt a destructive
   reverse migration without a tested procedure.
7. After the stabilization window, archive the old database and code according to
   retention policy; do not delete them merely because rollout completed.


16. RELEASE ACCEPTANCE CRITERIA

The Android release is not production-ready until all of the following are true:

- It is a native Kotlin/Compose app; the technician workflow is not a WebView.
- It installs and updates through the approved managed distribution channel.
- It works on physical fleet Galaxy Tab A9+ units in portrait, landscape,
  split-screen, and required DeX scenarios.
- It remains usable on the lowest-memory/storage fleet variant.
- It supports accessible text scaling, TalkBack, contrast, and 48 dp targets.
- No privileged secret is present in the APK.
- Authentication uses the approved mobile flow, secure token storage, expiration,
  rotation, revocation, and disabled-user enforcement.
- The mobile API is versioned, documented, tested, and backward compatible for the
  supported release window.
- Question submission is idempotent and answer attempts are durable/resumable.
- Losing connectivity or killing the app cannot create duplicate questions.
- The app never claims to answer offline and never labels an incomplete stream as
  a verified final answer.
- Machine selection is visible; changes are explicit; retrieval is enforced to the
  selected machine on the server.
- Only approved, current manual evidence can be used or opened by technicians.
- Citations, page evidence, warnings, revision conflicts, no-answer, retries,
  history, saved answers, and feedback pass end-to-end tests.
- Existing grounding, citation validation, prompt-injection, concurrency, and
  safety regression suites pass on PostgreSQL and the production RAG service.
- PostgreSQL backups, point-in-time recovery, object-storage recovery, migration,
  and rollback have been tested.
- Production monitoring, alerts, redaction, support, incident response, and corpus
  freshness monitoring are operational.
- A field pilot is signed off by technicians, product, security, and operations.


17. KEY RISKS AND MITIGATIONS

Risk: Treating “Android app” as a quick WebView conversion.
Mitigation: Native Compose is a release criterion; reuse backend behavior and API
contracts, not browser DOM code.

Risk: Rewriting UI and infrastructure simultaneously causes safety regressions.
Mitigation: Freeze technology-neutral regression tests first, deliver vertical
slices, and compare old/new answers and evidence against the same evaluation set.

Risk: Duplicate questions or ambiguous state under weak connectivity.
Mitigation: Idempotency keys, durable attempts, persisted event state, resumable
streams, and server-authoritative status.

Risk: The mobile app leaks proprietary manuals or credentials.
Mitigation: Server authorization on every evidence request, short-lived delivery,
minimal cache, Keystore-backed tokens, log redaction, secret scans, and MDM.

Risk: “Node.js migration” discards working Python retrieval safeguards.
Mitigation: Put the public/control plane in Node.js while extracting proven RAG and
ingestion logic into private Python services with unchanged behavioral tests.

Risk: Exact Tab A9+ fleet capabilities differ by SKU or update state.
Mitigation: Inventory devices before minSdk/performance commitments and test the
lowest-spec physical unit.

Risk: AI/provider latency makes the app appear frozen.
Mitigation: Durable asynchronous attempts, honest progress states, streaming,
timeouts, cancellation, reconnect, and provider-specific monitoring.

Risk: Migrated manual approvals or revision links are wrong.
Mitigation: Checksum/source-reference mapping, approval/current-revision reports,
machine coverage comparisons, retrieval evaluation, and signed migration review.

Risk: Old mobile releases become incompatible with the backend.
Mitigation: Versioned API, compatibility CI, staged deprecation, remote config, and
minimum-supported-version policy.


18. DECISIONS THE OWNER MUST MAKE BEFORE PHASE 1 EXITS

- Which identity provider will technicians use?
- Are the tablets company-owned and fully managed? Which MDM/EMM or Knox platform?
- Which exact Galaxy Tab A9+ SKUs, Android versions, and connectivity plans exist?
- Which cloud, region, data-retention period, backup policy, and incident owner?
- Is Google Drive confirmed as the continuing source of truth for manuals?
- May manual pages be cached locally, and for how long?
- Which AI provider(s) are approved, and what is the outage/fallback policy?
- Must screenshots, copy/paste, or external sharing be restricted by device policy?
- Is DeX or an external keyboard part of the supported technician workflow?
- How long must the PWA remain available after Android rollout?


19. SUGGESTED TEAM AND PLANNING RANGE

Minimum practical cross-functional team:

- Android engineer(s) experienced with Compose and managed enterprise devices.
- Node.js/TypeScript backend engineer.
- Python/RAG engineer familiar with the current retrieval and ingestion code.
- Product/design owner with direct technician access.
- QA/automation support with physical Tab A9+ devices.
- Security/identity and cloud/operations support at the relevant gates.

For a small experienced team, use approximately 12–18 weeks as an initial planning
range from Phase 0 through a limited field pilot. This is not a delivery promise.
Identity integration, production data migration, MDM readiness, corpus quality,
and field-test access can change the range substantially. Estimate each phase only
after Phase 0 decisions and baseline measurements are complete.


20. BUILDER IMPLEMENTATION RULES

1. Work through the phases and stop when you need input from the user.
2. Do not delete or weaken a current safety test to make a new implementation pass.
3. Do not begin with a mass rewrite. First build one vertical path: sign in, select
   an approved machine, submit one idempotent question, receive a durable grounded
   answer, and open one citation on a physical Tab A9+.
4. Record architecture decisions and API changes in the repository.
5. Include tests, migration/rollback notes, observability, and documentation in the
   same change as the feature; these are not post-launch tasks.
6. Do not call the project production-ready because an emulator demo works.
7. Never place secrets, manuals, embeddings, or an on-device LLM in the APK.
8. Retain Python for internal RAG/ingestion where it preserves the proven behavior;
   use Node.js/TypeScript for the public API and control plane as required.
9. Treat the server as authoritative for identity, machine scope, approval,
   revision, attempts, citations, and final answer status.
10. Demonstrate every release criterion with test output, a staging trace, a
    migration report, or a physical-device recording/checklist.
