FINAL CHANGES — ChatBot release review
======================================
Repository: https://github.com/cyagar/ChatBot
Revision reviewed: 6d5a59747f67097d0f5e384229087b877c0cd480
Review date: 2026-09-21
Scope: FastAPI/PostgreSQL backend, ingestion/retrieval/providers, admin web UI,
native Android client and Gradle/CI, scripts, migrations, tests and documentation.

OVERALL ASSESSMENT
------------------
This is a working, thoughtfully scoped Android/Google Drive/manuals prototype
with machine-filtered retrieval, review gates, invitation-based accounts,
persisted conversations, saved answers, and real device history in the docs.
It is close enough for a small supervised pilot only after the release-blocking
items below have been addressed and checked against the actual APK/backend.
Some current claims of evidence verification and evaluation accuracy are
stronger than what the code establishes. The backend test workflow will not
pass on a fresh checkout as configured. The ready-to-share APK and live server
were not supplied for inspection: this review cannot verify their actual
configuration, manual corpus, signature, or on-device behavior.

Priorities: P0 = fix before technician audience testing with operational
instructions; P1 = fix or explicitly contain during a supervised pilot;
P2 = follow-up cleanup/performance. A finding marked FIXED means a local
checkout change was made in this review; OPEN means feedback for the builders.
"Reproduced" denotes an offline probe with synthetic data and no live
credentials; "Static" denotes a source-level trace; "Conditional" requires
checking the chosen deployment or actual APK.

P0 — MUST ADDRESS BEFORE AN OPERATIONAL TECHNICIAN PILOT
--------------------------------------------------------
P0-01. Unsupported numbers and unsafe prose pass the "grounding" validator.
Status: OPEN; reproduced.
Code: backend/app/providers/base.py:125-200, 270-355; 372-394;
      backend/app/providers/anthropic_provider.py:71-111.
The validator extracts only some token forms, normalizes a unit to its bare
number, and checks substring presence anywhere in the concatenated cited
passages. In a synthetic excerpt stating "240 V; Do not operate with the cover
removed", it accepted all four unsupported claims: "5 psi", "24V", "240PSI"
and "-240 V". A single digit has no material token; "24" is a substring of
"240"; a unit mismatch is ignored; signs are stripped. It also accepted
is_no_answer text "Bypass the safety interlock and operate with the cover
removed" because it has no material numeric token, and accepted a warning
fragment with the negation removed. The no-answer prose and ordinary claims
are not semantic entailment checks. A live model can therefore make a
plausible but dangerous statement while citing a real manual.
Fix: parse signed numbers, tolerances and units as whole typed tokens, reject
unit mismatches and partial-number matches; require each quoted warning to
preserve the full warning including negation; constrain no-answer explanations
to fixed safe templates or check them too. Preserve a mapping of each claim/
step to its cited chunk, and add page-level technician verification prompts.
Use adversarial cases for 5 vs 50 psi, 24 vs 240 V, amperage vs voltage,
negative numbers, negated instructions, unsupported parts and compatibility.
Do not label the current heuristic "verified facts" or "zero hallucination".

P0-02. Approving an unready replacement can remove the working manual.
Status: OPEN; static.
Code: backend/app/api/routes_admin.py:329-389;
      backend/app/ingestion/pipeline.py:260-340; admin.js:418-450.
POST /documents/{id}/review accepts any active row, including failed,
unsupported, duplicate, or zero-chunk rows. It immediately deactivates all
other active documents with that source_ref. A newly ingested replacement has
machine links pending independent approval; the UI offers document approval
and link approval as separate operations. If the document is approved first,
the previous approved revision disappears and the new one may have no
approved machine link, leaving no retrievable manual. This is a realistic
normal-use sequence, not only an exotic concurrent write.
Fix: make promotion an atomic transition that verifies extracted indexed/
partial content, nonempty chunks, valid original file and at least one
approved applicable machine link; keep the old revision serving until those
conditions hold. Link/document review can remain separate internally, but
the admin action should present a readiness checklist and guard the
transaction. Exercise approval-first, link-first, failed replacement,
withdrawn link, and two-admin concurrent promotion on PostgreSQL.

P0-03. Metadata correction can approve previously rejected links.
Status: OPEN; static.
Code: backend/app/web/static/js/admin.js:254-280, 497-512;
      backend/app/api/routes_admin.py:186-219, 49-76.
Every Save correction sends all checked machine_ids, even if the administrator
changed only title or revision. The edit form starts checked for all existing
associations, including rejected and pending ones. The PATCH handler deletes
every document_machines row and recreates the sent IDs as approved with
confidence=1.0. A simple title correction can therefore silently override a
human rejection and expose a manual to a wrong machine.
Fix: send only dirty fields; include machine_ids only when associations were
explicitly edited and independently confirmed. Preserve review states for
unchanged links. If an admin intentionally overrides a rejected link, require
an explicit link review action and audit its previous state. Add an API/UI
regression: reject one link, change the title, assert it stays rejected and
unretrievable.

P0-04. Conversation and retry claims can remain stuck after a process death.
Status: OPEN; static.
Code: backend/migrations/0002_conversation_processing_lock.sql;
      backend/app/api/routes_chat.py:258-292, 740-765, 859-862, 899-946.
The committed is_processing boolean is cleared in a Python finally block.
A killed worker, lost DB connection in release, or shutdown between claim
and finally leaves it true indefinitely; all future questions/retries return
409. A failed retry can separately remain answer_status='retrying'. The 409
copy says "stop it" but no stop/cancel API exists.
Fix: store attempt ID, claimed_at/lease deadline, owner/fencing token and
terminal status. Bound total work; reclaim only expired attempts atomically
with fencing so a late old worker cannot write a second answer. Give the
technician a recovery or cancel action and expose attempt status. Test SIGKILL
after committed claim, startup/retry recovery, duplicate request, and two
workers claiming the same conversation. Keep the owner's one-question rule.

P0-05. Machine changes are not serialized with an in-flight answer.
Status: OPEN; static.
Code: backend/app/api/routes_chat.py:509-589, 920-944, 295-319;
      android/app/src/main/java/com/hmwagner/techmanual/ui/chat/ChatScreen.kt:380-391.
set_conversation_machine updates the conversation machine before checking
is_processing when there is no pending clarification. Old clarification chips
remain enabled in every loaded message. A tap can change the machine while an
answer for the previous one is in progress. Retry uses the conversation's
current machine rather than the original user's/answer's stored machine; the
history helper does not partition previous turns by machine. That creates
cross-machine context, mismatched headers and potentially wrong-model advice.
Fix: allow a selection only for the current pending clarification under the
same conversation lock, or require a new conversation on deliberate switch.
Use per-turn immutable machine_id during generation and retry; ensure history
for that answer stays in the same machine scope. Disable resolved chips.
Persist and display the answer's machine label, with a test switching while
a provider call is blocked and retrying an older answer after a switch.

P0-06. Android can lose the identity of a submitted question.
Status: OPEN; static, sequence derived from code.
Code: android/app/src/main/java/com/hmwagner/techmanual/ui/chat/
      ChatViewModel.kt:87-154, 167-202, 205-275.
After an ambiguous network failure the UI holds a UUID in pendingEcho. On
refresh, it clears that pending entry if the last loaded message has role
"assistant", without checking which request/answer it belongs to. When
sending is false, send() accepts a new question and overwrites pendingEcho.
Leaving/re-entering chat recreates its ViewModel and UUID, so a retry may
send the old question under a new key. On non-2xx, the failure handler also
overwrites a draft typed during the request with echo.content. These races
can lose a question or produce duplicate service calls.
Fix: persist pending attempt ID/content per conversation across navigation and
process recreation (SavedStateHandle or secure local storage); expose a
server-assigned user message ID or reply_to/attempt status; reconcile by that
ID rather than last role, and prevent an unresolved attempt from being
overwritten. Protect a newer draft from an older request's failure callback.
Test delayed POST + concurrent refresh, app kill/restart after server accept,
409 pending, and composing another question while one is uncertain.

P0-07. Android refresh can duplicate messages and possibly duplicate UI keys.
Status: OPEN; static, sequence derived from code.
Code: ChatViewModel.kt:87-154, 205-235; ChatScreen.kt:142-155.
A pull to refresh while a POST is in flight loads the server's persisted
messages into state. When that POST returns, performSend blindly appends a
synthetic user turn and the returned assistant answer to the refreshed list.
If GET already includes the assistant answer, that server ID appears twice in
LazyColumn(items, key={it.id}); if GET includes the user, the question appears
twice. Such a race can corrupt the visible history and cause a duplicate-key
Compose failure.
Fix: merge by stable server IDs and attempt ID, replace the local echo with
the acknowledged user turn, and discard an older refresh response using a
request generation counter. Add a deterministic delayed-response ViewModel
test covering GET both before and after answer persistence.

P0-08. Evidence requests can reopen a dismissed sheet or show the wrong page.
Status: OPEN; static.
Code: ChatViewModel.kt:343-386; ChatScreen.kt:497-557.
Each citation starts an uncancelled asynchronous fetch. Dismissing the sheet
does not cancel or invalidate it. Selecting citation B while A is still
loading lets A return last, with B's document ID/URL in state and A's evidence
or page. This is a direct risk when technicians use citations to verify
safety information.
Fix: cancel the previous Job and compare a monotonically increasing request
token plus (document_id, chunk_id) before applying any success/error. Reset
loading on dismissal. Drive an on-device test with A delayed behind B, then
dismiss during a load; no reopened/wrong manual image should appear.

P0-09. External deployment may discard manuals while keeping DB citations.
Status: OPEN; conditional on hosting choice.
Code: backend/app/config.py:16-19; backend/app/ingestion/pipeline.py:69-82,
      285-316; backend/Dockerfile; docker-compose.yml; scheduler.py:27-53.
The storage_backend setting has no implementation branch. Files and the Drive
cache live on local disk while PostgreSQL persists only the storage filename.
Docker Compose mounts ./data, so a single persistent host can work. The
owner's proposed Cloud Run deployment uses ephemeral instance files unless
a durable store is wired in; restart/scale/new instance could break manual
and page-image access even though retrieval and citations still work.
Unchanged files are skipped by ingestion, so a new empty local disk is not
automatically repopulated. The sleep-first timer also waits six hours after
startup for its first attempt.
Fix: before using ephemeral/replicated hosts, implement private durable
object storage, serve originals through it, verify migration/backfill, and
move scheduling plus the ingestion lock to a single coordinated worker/lease.
For the existing single-host Compose route, confirm mounted volume
permissions, persistence, recovery and a fresh-instance file-access test.
Owner-approved cold starts are separate from losing manual files.

P0-11. Retrieval evaluation script cannot run and its advertised measure is
       too permissive.
Status: OPEN; reproduced.
Code: backend/scripts/eval_retrieval.py:1-75, 76-131, 132-208;
      data/eval/ground_truth.json; README.md (old testing section).
It immediately raises AttributeError: Settings has no db_path_resolved.
Remaining code opens a SQLite backup, writes DB_PATH (unused with Postgres),
uses '?' SQL placeholders, and tries public registration without an invite.
Even if the first error were patched, evaluation could touch the configured
live PostgreSQL database; do not run a partly fixed script there. Its
"citation support" succeeds if a keyword appears in answer OR excerpt, so an
uncited invented answer word can pass; it does not validate claim-to-evidence

technician-written questions, wrong-machine cases, negatives and revisions.

retrieval pass until it runs and is independently scored.

P0-12. Release security settings do not reject an already copied example key.
Status: OPEN for deployments; example file corrected locally; reproduced.
Code: backend/app/config.py:92-117; backend/.env.example at reviewed commit.
The old example SECRET_KEY="change-me-to-a-random-64-char-string" is longer
than 32 and does not equal "dev-only-insecure-key". With otherwise plausible
settings, validate_for_startup accepts it under APP_ENV=production. Anyone
using that known string can mint valid signed session tokens when they know
a user ID/token_version; the DB checks mitigate stale/disabled users but do
not make a public signing key private. The new local example uses REPLACE_ME,
which production startup rejects on length, but old copied .env files remain.
Fix: reject a maintained list of known placeholders/low entropy defaults;
generate and store a unique random secret per environment; rotate any
deployment that ever used the example value, invalidating old sessions.
Verify APP_ENV, cookie Secure flag, allowed domains, HTTPS and session behavior
against the actual deployed backend, without disclosing its key.

P0-13. Old advice remains visible after an emergency manual withdrawal.
Status: OPEN; static, policy choice required.

P1-06. Admin UI CSP blocks its inline styles and event handlers.
Status: OPEN; static, browser confirmation needed.
Code: backend/app/main.py:110-133;
      backend/app/web/static/js/admin.js:106-417, 254-280.
CSP says style-src 'self' and script-src 'self', without unsafe-inline.
The admin template is served with those headers, but JS inserts many
style="..." attributes (including display:none on edit rows) and at least
one inline onclick="this.select()" attribute. CSP-compliant browsers ignore
blocked inline styles/handlers; edit rows may appear prematurely and layout
breaks. This is not solved by loosening the entire policy.
Fix: move inline declarations into app.css/admin.css classes, toggle classes
from JS, and use addEventListener for every handler. Check DevTools CSP
violations for all tabs and interactions in the deployed admin browser.

P1-07. Admin HTML encoding is unsafe inside attributes.
Status: OPEN; static.
Code: backend/app/web/static/js/admin.js:254-275, 558-562.
esc() puts text in a div and returns innerHTML, which escapes text nodes
but does not encode a double quote for an HTML attribute. It is used inside
value="..." and data-search="..." for document titles, revisions and machine
names. A quoted value can truncate the field and inject attributes/markup.
Strict CSP limits many script vectors but does not make malformed HTML safe.
Fix: create nodes and set .value/.textContent/dataset directly, or use a
separate proven attribute encoder. Add tests with quotes, ampersands, angle
brackets and pasted HTML in title/revision/model, rendered under strict CSP.

P1-08. Many admin actions fail without a visible recovery path.
Status: OPEN; static.
Code: backend/app/web/static/js/admin.js:85-104, 418-555.
Some invite creation code catches errors, but loading tabs and approving
documents/links, deactivating, reindexing, saving metadata and running the
query often await api() without try/catch or disabled/loading state. An
expired admin cookie, 409, 422, source timeout, or deployment restart can
leave an action apparently unresponsive; double taps may compound it.
Fix: centralize error display with correlation ID/status and safe retry

conflict, and handle 401 by returning to admin login. Test empty corpus,
expired admin session and failed reindex. Expose human review of document

P1-09. Real legacy Word files are always routed to unsupported extraction.
Status: OPEN; reproduced on synthetic OLE signature.
Code: backend/app/ingestion/extractors.py:351-428.
OLE files sniff as "ole"; resolve_file_type trusts the sniff over a ".doc"
extension; extract() dispatches to extract_legacy_doc only for "doc".
An actual binary .doc therefore takes the unsupported branch. Conversely
all ZIP OOXML signatures are labeled "docx", so .xlsx/.pptx may be sent to
the wrong parser. The documented "legacy .doc supported" claim is false.
Fix: inspect OLE streams or safely classify expected .doc OLE with the
extension and WordDocument stream; inspect ZIP member names to distinguish
.docx from other OOXML; mark unknown containers unsupported explicitly.
Test with a genuine tiny legacy .doc, DOCX, XLSX and renamed PDFs, including
extracted text/chunks and safe failure messages.

P1-10. Metadata reindex can overwrite reviewed associations and bad reads.

The reindexer calls extract() and never checks an ExtractedDocument status

link, manual override, same model across manufacturers and failed extraction.

P1-14. Retry and ingestion state are not robust to interruptions.
Status: OPEN; static, requires database/device confirmation.

      backend/app/ingestion/scheduler.py:27-56;

P1-18. Cookie jar does not fully enforce cookie semantics.
Status: OPEN; static.
Code: android/.../network/PersistentCookieJar.kt:28-90.
loadForRequest checks only exact host and expiry, not Cookie.matches(url)

encrypting a newly received cookie fails, the old ciphertext is left in
preferences; after restart an older session can be restored.

entries for hasSession, and clear old persisted ciphertext on encryption
failure. Test domain/path/TLS matching, concurrent save/load and Keystore
failure/recovery on device. Release manifest already disables cleartext;
this is defense against future host/path changes and stale sessions.
